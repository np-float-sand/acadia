## What Was Done This Session

### Goal
PJM T&D utilities were actively destroying alpha because LMP/GSI signals don't apply to rate-regulated companies. The fix: make the factor model business-model-aware.

### Solution
Three architectures tested:
1. **Hard switch** (winner): `pass_through < 0.5` → ICR signal; `pass_through >= 0.5` → stress beta
2. **Revenue mix**: blend by `pass_through` coefficient
3. **Dual-track**: same blend but z-scored within peer subgroups

Hard switch wins because the binary routing is cleaner than blending noisy ICR data into a well-calibrated stress beta signal.

### Root cause of PJM problem (confirmed)
Rate-regulated T&D utilities earn revenue set by state rate cases, not LMP. The stress beta has zero mechanistic link to their earnings. Adding ICR as their primary signal captures refinancing risk during rate stress events instead.

### Key Analytical Finding: ICR ≠ Data Centers
The hard-switch architecture routes PJM T&D utilities to an ICR signal (financial fragility). This does NOT capture data center load growth. ICR identifies which utilities are fragile under rate stress; it says nothing about which utilities benefit from data center demand.

Key distinction:
- **D (Dominion)**: Massive data center territory (Northern Virginia #1 global DC market) → ICR reflects debt load from nuclear build, NOT DC growth
- **PEG (PSEG)**: NJ corridor (Amazon, Google) → ICR reflects financial leverage, not DC positioning
- A utility with poor ICR but enormous DC load growth in its territory would incorrectly score as a short

### Phase 2 Signal Decision
Data center / interconnection queue signal is the priority regulated-utility signal to build next. ICR is placeholder. Data sources:
- **PJM interconnection queue**: public downloadable, shows queued large-load requests by zone — directly maps to D/PEG/EXC service territories
- **EIA-861**: annual survey, load by customer class (industrial/large commercial) — tracks realized load growth

## Session Update — 2026-07-06 (Data Center Signal Brainstorm)

### Status
Brainstorming in progress. Approach chosen, data sources identified. Design doc and implementation plan NOT yet written. Resume at "Present design" step.

### Decision: Approach C — Dual-Component DC Load Signal
Replace ICR in the regulated utility signal slot of `build_factor()` with a two-component data center load signal:
- **Level (60% weight):** ISA-signed MW in generation queue / utility peak load — structural DC positioning
- **Momentum (40% weight):** 3-month change in total queued large-load MW — captures new announcements
- **Target IC horizon:** 63d primary, 21d secondary
- **Replaces:** ICR as the regulated-path signal. ICR remains available via `--regulated-signal icr` flag.

### Data Sources (v1 — two layers only)

**Layer 1 — Realized zone load growth (ALREADY IN CACHE)**
- Source: gridstatus PJM load data, already fetched monthly via `fetch_load("PJM", ...)`
- Signal: trailing 12-month avg daily load / prior 12-month avg daily load, by PJM zone
- Maps to tickers via `TICKER_NODE_MAP[ticker]["load_zones"]`
- Zero new infrastructure needed

**Layer 2 — Generation queue by zone (NEW — gridstatus `get_interconnection_queue()`)**
- Source: gridstatus PJM interconnection queue, updated weekly
- Filter: large projects (>100MW), active status or ISA-executed, in DC-heavy zones
- Level component: ISA-signed MW / utility peak load (from EIA-860 or existing load data)
- Momentum component: 3-month change in total queued MW
- gridstatus already imported in codebase

**Layer 3 — PJM Large Load Additions workshop reports (DEFERRED — v2)**
- Annual PDF reports with zone-level DC MW projections
- Requires PDF scraping, annual frequency — not worth for v1

### What PJM Actually Tracks (Research Finding)
- **No separate load interconnection queue.** Data centers connect at distribution level through local utilities — they don't file a PJM queue entry.
- **Co-located generation queue:** When hyperscalers build dedicated generation (e.g. Microsoft/Three Mile Island), that generator appears in the standard generation queue in DOM/PSEG/COMED zones. This IS the proxy signal.
- **LLA process:** PJM has a "Large Load Additions" stakeholder process with zone-level MW data in annual workshop PDFs. Data is real but requires manual scraping — deferred.

### Zone → Ticker Mapping (Already Built)
`TICKER_NODE_MAP[ticker]["load_zones"]` already maps each PJM ticker to its zones:
- D: `["DOM"]` — Northern Virginia, largest DC market globally (~250 DCs, 130 under development)
- PEG: `["PSEG"]` — NJ corridor (Amazon, Google)
- EXC: `["PECO", "BGE", "PEPCO", "COMED"]` — IL/PA/MD/DC/NJ, medium DC exposure
- FE: `["ATSI", "JCPL"]` — Ohio/NJ, lower DC exposure
- AEP: `["AEP", "DAYTON"]` — Ohio/WV, low DC exposure
- PPL: `["PPL"]` — PA/KY, low DC exposure
